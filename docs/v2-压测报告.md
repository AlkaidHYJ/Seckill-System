# v2 压测报告

> 测试日期：2026-10-18
>
> 本轮验证 Redis Lua 预扣 + RabbitMQ 异步落库链路。采用 2 轮预热（r0/r1）+ 3 轮正式压测（r2/r3/r4），正式结果取 r2/r3/r4 中位数。所有轮次使用同一应用进程、同一机器、同一 JMeter 场景和 Hikari pool=10。

## 1. 测试范围

本轮覆盖：

- Redis Lua 原子预扣库存
- 用户 SETNX 一人一单
- `CREATING` 状态、owner Key 和 `seckill:creating` ZSET
- RabbitMQ Publisher Confirm 后异步消费
- Consumer 幂等状态判断
- MySQL 条件扣减和异步插单
- Redis/MySQL/MQ 最终收敛
- HTTP 受理接口性能

本轮不覆盖：

- CREATING 超时补偿触发（需要人为制造 5 分钟超时窗口）
- 支付超时关闭
- v4 对账任务
- 限流和秒杀 token/path

## 5. 额外功能验证

### 5.1 rollback.lua 幂等

使用独立测试订单执行 rollback Lua：

- 首次执行返回 `0`
- 库存从 5 恢复为 6
- 用户标记删除
- `order:state` 变为 `FAILED`
- `seckill:creating` 成员删除
- 第二次执行返回 `1`
- 库存保持 6，没有重复回滚

- Maven 编译通过，`git diff --check` 通过

## 6. 问题与结论

### 6.1 已发现问题

P99 正式轮中位数为 501ms，比设计目标 500ms 高 1ms。该差异处于测量波动范围附近，但按预先约定不能判为通过。当前不建议为了压低 1ms 修改业务逻辑，应在同环境重复正式轮确认是否稳定复现。

### 6.2 测试限制

1. 本轮未人为等待 300 秒触发 CREATING 超时补偿，因此补偿 Job 只完成编译和 rollback Lua 行为验证，没有得到定时任务实跑样本。
2. 本轮没有支付请求，不验证 `PAID` 状态。
3. 压测机、应用、MySQL、Redis、RabbitMQ 同机运行，QPS 只用于同环境 v1/v2 相对比较，不能外推生产容量。
4. 未单独采集 CPU、GC、数据库锁等待和 RabbitMQ 消费时延，因此不能对瓶颈做资源级归因。

## 7. 结论

v2 本轮性能和正确性结果为：

- **QPS 达标**：393.7，中位高于目标 300。
- **系统稳定性通过**：0 5xx、0 连接失败、0 JTL 重复写入。
- **异步一致性通过**：100 条订单全部落为 `UNPAID`，MySQL/Redis 库存均为 0，ZSET 和订单队列均清空。
- **P99 临界未达标**：501ms，比 500ms 目标高 1ms，需要后续同环境复跑确认。
- **补偿逻辑单元验证通过**：rollback Lua 重复执行不会重复增加库存。

v2 本轮整体判定：**核心链路通过，P99 性能指标临界未通过，保留一次复跑确认项。**
