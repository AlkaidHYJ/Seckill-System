做得好的：

- **正确性证据链闭环**：jtl（客户端视角）与 `analyze_log.py`（服务端 UPDATE/INSERT 计数）两边逐轮互相吻合，diff=0 不是"恰好对上"而是被双向验证；这让"无超卖/无少卖"的结论可辩护。
- **验收口径提前拍板并落到工具里**：D2 错误率拆分通过 jmx 内置 JSR223 改判实现，避免了"50% 业务拒绝被算成故障"的错误结论；v1 基线 `pool=10` 顶住诱惑没调大，v2 对比才有说服力。
- **及时止损而非硬解释脏数据**：发现 run3/run4 同进程差 2.3 倍后没有归因给连接池，而是重跑 6 轮并建立"预热轮作废 + 后三轮中位"规则，基线从"单轮快照"升级为"收敛后的中位值"（相邻轮增幅已收敛到 3.3%）。
- **工装沉淀**：`analyze_jtl.py`（含有效性自动判定）、`analyze_log.py`（按 jtl 时间窗自动回溯日志交叉验证）、`analyze_tomcat_threads.py`（线程编号 vs distinct 并发）、`gen_users.ps1`、`run_sql.ps1` 全部进 `docs/loadtest/`，v2 可直接复用同口径。
- **参数定性用三条独立证据互证，不靠猜**：配置源穷举（yml/Dockerfile/compose/pom/IDE/进程命令行/argfile 全零命中）+ 日志 distinct 线程数（每轮 ≤200、两轮恰 200）+ `jcmd Thread.print` 空闲态 10 条 → 才敢下"默认值、无外部覆盖、`exec-390` 是累计编号"的结论；同时**诚实承认 actuator 这条路走不通**（`exposure` 未含 `metrics`），没有把"推断"写成"实测"。
- **功能验证与压测结论物理隔离**：`2010`/`PAID` 两条分支单列报告 §4 并标注"手动 / 压测未覆盖 / 回滚未测 / 留 v2"；对无法读数的地方（响应体 code 未落日志、现库 PAID 已被清）明确写"由代码路径推定""无法用现库复验"，不用推测冒充证据。

做得不好的 / 意外踩坑：

- **目标写了但没实现**：G6/G7 在设计阶段被当成"v1 范围"，实际编码时只建表没写 job，直到填复盘才暴露——以后 ADR/目标表应带"实现载体（类名/任务名）"字段，避免"表存在 = 功能存在"的错觉。
- **"0 次触发"被误读成"已验证"**：限购与幂等路径本轮根本没被打到，第一版报告草稿差点写成"限购通过"。
- **压测流程的执行纪律是数据质量的主因**：昨天的 3 个坑（双写、过期 token、多轮叠加）全是流程问题而非技术问题，成本是整整一天的无效数据。
- **同机压测的天花板与噪声**：JMeter + 应用 + MySQL 容器抢同一台 8C16T，P2 的连接拒绝虽已排除"参数被外部覆盖"，但是否由本机端口/backlog 抖动引起仍无法证实，绝对值不可外推。
- **可观测性缺配让取证绕了远路**：`management.endpoints.web.exposure.include` 只放 `health,info`，本该一条 `GET /actuator/metrics/tomcat.threads.config.max` 就能定性的问题，最后靠日志计数 + `jcmd` 反推；而未映射路径被兜底成 500（P7）又额外制造了"看起来像服务端故障"的噪声。以后新项目第一天就该把 metrics 暴露与 404 语义定好。
- **单轮 200 样本的统计意义有限**：只能报"当前快照 + 多轮中位"，不能报"稳定值"。
