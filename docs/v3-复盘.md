## 2. 关键决策

### ADR-017：秒杀 token/path

- 新增 `POST /api/seckill/activities/{activityId}/token`；用 `SecureRandom` 生成 32 字节 token 与 24 字节 URL-safe path（192 bit 熵）。
- Redis 存 `seckill:token:{SHA-256(path)}` Hash（`token/userId/activityId/expiresAt/status=READY`），TTL 60 秒；Redis 不存明文 path。
- 购买接口改为 `POST /api/seckill/activities/{activityId}/buy/{path}`，token/path/JWT userId/URL activityId 必须互相匹配；`seckill_full.lua` 在一次执行内完成全部校验并将 status 置 `USED`，再执行 v2 的限购/库存预扣和 CREATING 写入。
- 凭证失败统一返回 2006，不区分不存在、篡改、跨用户、跨活动、已用、过期，避免泄露凭证状态。
- 库存不足不消耗 path（返回 2008），允许有效凭证在库存短暂变化时重试。

### ADR-018：Redis ZSET 滑动窗口限流

- `SeckillRateLimitInterceptor` 在 JWT 鉴权之后、Controller 之前执行，仅拦截 `/buy/*`。
- 用户维度 `seckill:limit:user:{userId}:{activityId}` 默认 5/秒；IP 维度 `seckill:limit:ip:{ip}` 默认 20/秒，可用环境变量覆盖。
- 同一 Lua 原子完成清理、计数、判断与写入；任一维度超限即返回 429/2013，不进入 `SeckillService`、不执行 `seckill_full.lua`、不扣库存。
- Redis 不可用时 fail-close（返回 5002），不允许绕过限流进入秒杀链路。
- 商品维度本批不启用。

## 4. v3 新暴露的问题

### 4.1 QPS 口径不统一（已拍板）

v2 每轮 200 个 buy 样本，v3 每轮 400 个（token+buy）样本。已拍板：**主口径为 buy 受理 QPS（v3 469.5，对比 v2 393.7，+19%），目标「QPS >= 393.7」绑定主口径判定为达标**；端到端整体 QPS 199.6 为副口径，因每用户多一次 token 往返而低于 v2，仅作参考。已固化到报告顶部「统计口径」章节。

### 4.2 QPS 统计方式与 JMeter 不一致（已拍板）

已拍板：QPS 统一采用 JTL span 口径（对齐 v2，已用同一脚本对 v2 的 r2/r3/r4 复现 365.0/393.7/406.5）；**JMeter Summariser 的瞬时吞吐（r2≈134/s）不作为验收口径**。已固化到报告「统计口径」与 6.5 节。

### 4.3 IP 维度限流未实测

同机 200 用户共享同一个 `remoteAddr`，正式压测将 `seckill.rate-limit.ip-per-second` 临时调高至 10000 以避免误杀，导致 IP 维度无法触发。当前 IP 限流仅有代码证据（`getRemoteAddr`、滑动窗口 1000ms），缺实测样本，属已知限制。

### 4.4 瞬时建连拒绝（r3 保留有效轮）

r1/r3 在 200 线程同时建连的瞬间出现建连拒绝（51 / 33 次 `Connection refused`，`HttpHostConnectException` 并连带同数量 `URISyntaxException`），r2/r4 无此现象。已拍板判定为 **accept backlog 偶发**：瞬时建连超过服务端 accept 队列深度，属环境/接入层限制，非业务错误（5xx=0）。因此 **r3 保留为有效轮**；v4 调大 `accept-count` 验证。

### 4.5 r0 早期预跑无效

r0 因限流阈值未调高出现 195 个 429，且当时 JMX 尚未采集业务码，未纳入统计。需要固化「先调阈值、再跑轮次」的准备流程，避免无效轮次。

## 5. 留给 v4 的 backlog

### v4

- `UNPAID -> CLOSED_TIMEOUT` 超时取消与库存回补。
- Redis/MySQL/订单聚合定时对账与告警。
- DLQ 消息查看、人工重放与处理结果记录。
- 针对 Publisher Confirm 不确定窗口的差异检测与恢复流程。

### v3 遗留

- **高并发突发建连偶发拒绝，v4 调大 accept-count 验证**（r1/r3 各 51/33 次 Connection refused）。
- IP 维度限流的独立实测（多源 IP 或临时降低阈值后用独立 key 构造）。
- 量化 `token -> buy -> UNPAID` 端到端收敛时延的 P50/P95/P99。
- 补齐 CPU、GC、MySQL 锁等待、RabbitMQ 消费延迟等资源级指标。

## 6. 已知代价

- 正常下单多一次 token 往返，端到端请求数翻倍、整体 QPS 下降，客户端交互更复杂。
- Redis 承载 token Hash、限流 ZSET、库存与用户标记，成为更重的单点；限流 fail-close 增加了可用性耦合。
- IP 维度限流依赖 `remoteAddr`，共享 NAT 下可能误杀；可信来源需在网关层治理。
- 库存不足不消耗 path，可能被用于在有效期内多次尝试（业务语义权衡）。
- 同机压测仅用于 v2/v3 相对比较，QPS 不能外推生产容量。
- 失败消息进入 DLX 后仍需运维手工介入。
