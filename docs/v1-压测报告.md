> 结论：v1 的瓶颈**不是连接池容量**，而是同一活动行的条件扣减串行化（热点行锁）+ 接入层/Tomcat 排队。这条结论让 v2 对比更有说服力——v2 若只加大连接池不会有任何提升，必须做 Redis 原子预扣。

### 3.4 超卖/少卖判定

- **无超卖**：`available_stock=0`（无负值）、有效订单 100 = `total_stock` 100、`uk_activity_user` 与 `uk_order_no` 分组均 0 行 → 条件 UPDATE + 热点行锁 + 唯一索引三层防护在 200 瞬时并发下成立，与响应侧"100 成交 / 100 库存不足"完全吻合。
- **无少卖**：`diff = 100 − 0 − 100 = 0` → `@Transactional` 下唯一键冲突整体回滚（含已做的库存扣减），不存在"拒绝但库存已扣"的缺口。v2 改异步落库后此项需重新验证。

### 4.3 本节限制（必须与压测结论分开解读）

1. **这两项是手动功能验证**：单请求、人工构造数据、无并发，不能外推为"并发下同样成立"。
2. **压测场景未覆盖**：6 轮压测中每个 userId 每轮只发 1 个 buy 请求，业务码 `2010` 触发 **0 次**（见 2.2 分布表），支付接口从未纳入压测样本 → 第 3 节的 50% 拒绝全部是 `2008`，与本节 `2010` 属**不同代码分支**。
3. **唯一索引冲突时的库存回滚未测**：4.1 中 `deductStock Updates: 1` 之后随事务回滚，理论上库存应复原（`@Transactional(rollbackFor = Exception.class)`），但**未采集回滚后的 `available_stock` 快照**；"拒绝但不丢库存"目前只有压测后总量对账（diff=0）间接支撑，**单请求级别的回滚未验证**。
4. **留 v2 并发场景验证**：v2 需补"同一用户并发重复 buy"（验证 `uk_activity_user` 在高争用下只成交 1 单、且库存不漂移）与"并发支付 / 超时关闭竞态"两组用例，并把 `2010` 触发次数、`PAID` 订单数、回滚后库存差值纳入每轮对账。

## 5. 结论

**v1 PASS**（正确性 5/5 全绿；性能基线 QPS 152.6 / P95 1293 ms / P99 1304 ms，样本已进平台期，可作为 v2 对照组基线）。

证据链：
1. **正确性**：r5 对账 `100 = 0 + 100`、diff=0、无负库存、无重复订单；5 个有效轮的服务端写入量（200 UPDATE + 100 INSERT）与 jtl 的"100 成交 + 100 拒绝"逐轮吻合，客户端与服务端两边数据互相印证，不存在统计口径造假。
2. **稳定性**：6 轮共 1200 请求，服务端 **0 条 ERROR/WARN、0 个 5xx、0 次连接池超时、0 次死锁/锁等待超时**；r4/r5 连 53 个连接拒绝也未复现。
3. **瓶颈定位**：P99 1304 ms、QPS 152.6，而 TCP connect 仅 55~71 ms → 时间花在服务端串行排队（同一行 `UPDATE ... WHERE available_stock>=1` 的写锁），不是网络、不是连接池。拒绝路径 min 118~121 ms 显著低于成交路径 max 1309 ms，符合"抢不到锁 → 读到库存 0 → 快速失败"。
4. **数据可信度**：单轮仅 200 样本、且为同机压测，绝对值不外推；采用"预热轮作废 + 后三轮中位"规则已消除冷启动污染（增幅收敛到 3.3%）。
5. **接入层参数已查明**（10-16 补充取证）：Tomcat `threads.max=200` / `min-spare=10` / `accept-count=100` 均为**默认值且无任何外部覆盖**；历史日志的 `exec-390`/`exec-1049` 是线程工厂的**累计编号**而非并发线程数（每轮实测 distinct 线程数 ≤200），与 `maxThreads=200` **不矛盾**（取证过程见 §6.1）。这**排除了 Q1 的"参数被外部覆盖"猜想**，但 r1 那 53 次连接拒绝的根因仍未定性——剩余候选为本机 listen backlog / 临时端口抖动（与 Q3 同因），不作无证据的定论。
6. **功能语义另有手动验证**：重复下单 `2010` 与支付流转 `PAID` 两条分支在压测样本中触发 0 次，改由第 4 节的手动验证证据支撑，且明确标注了不可外推到并发场景。

### 6.1 Q1 专项取证：Tomcat 接入层参数实际生效值（2026-10-16）

**结论：`threads.max=200`、`threads.min-spare=10`、`accept-count=100`、`max-connections=8192`，全部是 Spring Boot 嵌入式 Tomcat 默认值，无任何外部覆盖；`exec-390` 与 200 不矛盾。**

| 参数 | 实际值 | 判定依据 | 性质 |
| --- | --- | --- | --- |
| `server.tomcat.threads.max` | **200** | 配置源零命中 + 每轮压测 burst 内 **distinct 工作线程数恰好 ≤200**（r0=200、r2=200、r3=199、r4=199、r5=199） | 实测钉死 |
| `server.tomcat.threads.min-spare` | **10** | 压测结束后 `jcmd <pid> Thread.print` 只剩 **10 条** `http-nio-8080-exec-*`（编号 997~1049）→ 池回落到最小值 | 实测钉死 |
| `server.tomcat.accept-count` | **100** | 未配置 → 默认 100；与 r1 的"服务端只服务 147 个 + 客户端被拒 53 个"数量级吻合（200 齐发超出可即时受理范围时，超出部分进入 backlog，再超出即 RST） | **默认值推断，未直接观测** |
| `server.tomcat.max-connections` | 8192 | 未配置 → 默认值；本机 NIO Acceptor 未成为约束 | 默认值推断 |

**配置源穷举检索（全部零命中 Tomcat 参数）**：

| 检索位置 | 结果 |
| --- | --- |
| `application.yml` / `application-dev.yml` / `application-prod.yml` | 无 `server.tomcat.*` 任何键 |
| `Dockerfile` | 无 `JAVA_OPTS` / `SERVER_TOMCAT_*` / `-D` 参数 |
| `docker-compose.yml` | 只有 MySQL 容器，应用未容器化运行，无相关环境变量 |
| `.mvn/settings.xml`、`pom.xml`（spring-boot-maven-plugin 配置段） | 无 `jvmArguments` 覆盖 |
| `.vscode/launch.json` | 仅有浏览器启动配置，无 JVM args |
| 运行中进程 PID 35700 命令行 | 仅 `-XX:TieredStopAtLevel=1 -cp @C:\...\javaArgsXXX.argfile`；argfile 内只有 classpath，**无 `-Dserver.tomcat.*`** |
| `.env` | 只有 DB/Redis/JWT 变量，无 Tomcat 项 |

**`/actuator/metrics/tomcat.threads.config.max` 无法查证（重要限制）**：
`application.yml` 中 `management.endpoints.web.exposure.include=health,info` **未包含 `metrics`** → 该端点未暴露。实测（10-16 16:49~16:50）：

```
HTTP GET /actuator/health                          -> 200
HTTP GET /actuator/info                            -> 200
HTTP GET /actuator/metrics                         -> 500
HTTP GET /actuator/metrics/tomcat.threads.config.max -> 500
HTTP GET /actuator/env                             -> 500
HTTP GET /api/not-exist-path                       -> 500
```

即：**指标端点不仅不可用，还返回 500 而非 404** —— `GlobalExceptionHandler` 对 `Exception` 的兜底把 Spring 的 `NoResourceFoundException`（404）吞成了 `code=5001 / HTTP 500`。这是本次取证顺带暴露的**新问题**（记入 §6.2 Q8）。因此线程池上限只能靠"日志 distinct 线程数 + jcmd"两条实测路径确定，无法靠 actuator 直读。

**`exec-390` 之谜已解**：Tomcat `TaskThreadFactory` 的线程名编号是**进程生命周期内的累计计数器**，线程销毁后编号不回收、不复用，因此编号可以远大于同时存活的线程数（也就是 `maxThreads`）。日志实测证据链：

| 轮次（2026-10-16） | 该轮 exec 编号区间 | 该轮 distinct 线程数 |
| --- | --- | --- |
| r0 15:59:46 | 1 ~ 200 | **200** |
| r1 16:04:10 | 4 ~ 337 | 147（=200−53 未到达） |
| r2 16:07:36 | 261 ~ 527 | **200** |
| r3 16:09:48 | 474 ~ 716 | 199 |
| r4 16:23:07 | 657 ~ 905 | 199 |
| r5 16:25:00 | 657 ~ 1049 | 199 |

> 每轮 distinct 均 ≤200 且两轮**恰好** 200 → `maxThreads=200` 被钉死；编号跨度可远超 200（10-14 全天最大编号 10、10-15 最大 390、10-16 最大 1049，编号>200 的日志行共 14744 条）→ 编号无上限，与并发数无关。**结论：不存在外部覆盖，`exec-390` 不矛盾。**

**取证工装**：`docs/loadtest/analyze_tomcat_threads.py`（合并当前 log 与 gz 归档，按天、按 jtl 时间窗统计 exec 线程编号区间与 distinct 数）。
