## 统计口径

本节为全篇 QPS 与目标判定的统一口径，先行约定，避免后续摇摆。

- **主口径（buy 受理）：QPS 469.5**，对齐 v2 的 393.7（对比 **+19%**）。目标「正常用户 QPS >= v2 393.7」按此口径判定，结论为**达标**。该口径仅统计 `buy/{path}` 采样器（200 样本/轮），与 v2 的 200 个 buy 样本一一对应，可**直接比较**。
- **副口径（端到端整体）：QPS 199.6**，统计每轮 400 样本（200 token + 200 buy）。低于 v2 的原因是**每个用户新增一次 token 往返**（同 200 用户需 400 次请求），请求模型与 v2 不同，**仅作参考，不与 v2 做达标比较**。
- **统计方式**：所有 QPS 均取 JTL 时间窗 **span 口径**：`span = max(timeStamp + elapsed) - min(timeStamp)`，`QPS = 样本数 / span`。该口径与 v2 一致（已用同一脚本对 v2 的 r2/r3/r4 复现 365.0 / 393.7 / 406.5）。
- **不作为验收口径**：JMeter Summariser 输出的瞬时吞吐（r2≈134/s）含线程启动/ramp 时间，偏低，**仅作观测参考，不作为验收依据**。

### 6.3 QPS 口径说明（主/副口径）

v2 场景为「200 线程各下单一次」，每轮 200 个 buy 样本，报告 QPS 393.7 即该 200 样本的 span 口径吞吐。v3 为「每用户先取 token 再 buy」，每轮 400 样本。判定采用以下两个口径：

- **主口径（buy 受理，与 v2 可比）**：v3 buy QPS 中位 469.5，高于 v2 的 393.7（**+19%**），说明下单受理链路本身没有退化。目标「正常用户 QPS >= 393.7」按此口径判定为**达标**。
- **副口径（端到端整体）**：v3 整体 QPS 中位 199.6，低于 v2，因为每个用户新增一次 token 往返，同样 200 用户需要 400 次请求。该口径请求模型与 v2 不同，**仅作参考，不与 v2 做达标比较**。

主/副口径的定义与统计方式见报告顶部「统计口径」章节。

### 6.4 r3 建连拒绝说明（r3 保留有效轮）

r3 出现 33 次 `Connection refused`（`HttpHostConnectException`，token）并连带 33 次 `URISyntaxException`（buy），发生在 200 线程同时建连的瞬间，判定为 **accept backlog 偶发**：客户端瞬时建连超过服务端 accept 队列深度所致，**非业务错误**（5xx 为 0、无超卖/重复、对账 diff 为 0）。r2/r4 同配置无此现象。因此 **r3 保留为有效轮**，纳入 r2/r3/r4 中位数统计；后续在 v4 通过调大 `accept-count` 验证（见复盘 backlog）。r1 同类现象 51 次，r1 为预热轮，不影响正式结论。

### 6.5 QPS 统计方式

所有 QPS 均由 JTL 的 `timeStamp`/`elapsed` 按 span 口径计算：`span = max(timeStamp + elapsed) - min(timeStamp)`，`QPS = 样本数 / span`。该口径与 v2 一致，并已用同一脚本对 v2 的 r2/r3/r4 复现出 365.0 / 393.7 / 406.5，与 v2 报告吻合。**JMeter Summariser 的瞬时吞吐不作为验收口径**：其 elapsed 含线程启动/ramp 时间（r2≈134/s），仅作观测参考。

## 8. 问题与修复记录

### 已修复：默认不信任 XFF

限流 IP 使用 `HttpServletRequest.getRemoteAddr()`，不再读取客户端可伪造的 `X-Forwarded-For`。经过可信网关时，需要在网关层完成来源地址治理，应用层不直接信任该 Header。

### 待确认问题（本次处理情况）

1. **IP 维度未实测**：200 用户同机压测共享同一个 `remoteAddr`，正式压测已将 `seckill.rate-limit.ip-per-second` 临时调高至 10000 以避免误杀，因此 IP 维度限流本轮无法触发；IP 限流仅通过读代码确认（`getRemoteAddr` 采样、滑动窗口 1000ms），缺实测证据。属已知限制。
2. **token 与 buy 分列统计**：本轮已分别统计（见 6.2），未只看总事务时间。
3. **MQ 竞态**：每轮对账均在等待订单队列清空后执行（每轮结束等约 10 秒），断言不早于收敛。
4. **瞬时建连拒绝**：r1/r3 批量建连出现建连拒绝（51/33 次），说明单机 200 并发瞬时建连会触及 TCP backlog；生产需评估接入层与连接数配置。

## 9. 结论

v3 本轮性能、正确性与防刷结果为：

- **防刷全部通过**：无 token/path（401/1005、400/1002、400/2006）、path 重放（第二次 400/2006、token=USED）、用户超限（5 次 429/2013）全部被正确拒绝，且均未扣库存、未产生订单、未写 `seckill:creating`。
- **正确性通过**：超卖 0、重复订单 0、`total_stock - available_stock - valid_orders = 0`，Redis/MySQL/MQ 三方收敛一致，正式轮 MySQL `UNPAID=100`、库存全清、队列与 ZSET 均空。
- **buy 受理性能通过**：buy 口径 QPS 中位 469.5，高于 v2 的 393.7；P99 中位 397 ms，优于 v2 的 501 ms。
- **端到端整体 QPS 低于 v2**：整体 QPS 中位 199.6，因每用户新增一次 token 往返，口径与 v2 不可直接比较。
- **两项已知限制**：IP 维度限流未实测；r3 出现 33 次瞬时建连拒绝。

v3 本轮整体判定（主口径·buy 受理）：**防刷、正确性与 buy 受理性能全部通过——buy 受理 QPS 469.5（对比 v2 393.7，+19%）、P99 397 ms（优于 v2 501 ms）、超卖/重复/5xx/diff 全 0；端到端整体 QPS 199.6 因每用户多一次 token 往返低于 v2，属口径差异，仅作参考。**
