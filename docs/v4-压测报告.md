## 统计口径

沿用 v3，主口径统一为 **buy 受理 QPS**：

- **主口径（buy 受理）**：统计 `buy/{path}` 采样器（200 样本/轮），对齐 v3 的 469.5、v2 的 393.7，可直接比较。护栏「≥ v3 的 90%（≥ 422）」「P99 ≤ v3 的 120%（≤ 476 ms）」按此口径判定。
- **QPS 统计方式**：JTL **span 口径** `span = max(timeStamp + elapsed) - min(timeStamp)`、`QPS = 样本数 / span`，与 v2/v3 一致；JMeter Summariser 瞬时吞吐不作验收口径。
- **统计范围**：性能中位取正式轮 **r1~r4**（r0 预热不计入）。

## 7. 场景 4：三方对账告警（本批功能轮实测，2026-10-21）

人为注入 **Redis 单侧差异**（只改 Redis，不改 MySQL），验证 JOB-03「1 周期内检出 + 只告警不改数」。以下为实测数据：

**注入**：`redis-cli SET seckill:stock:2 99`，注入时间 21:12:34.654（MySQL 保持 100 不动）。

**检出**（record 完整行，JOB-03 于下一 tick 21:17:31 写入）：

- **日志 ERROR**：`JOB-03 inconsistency detected, activityId=2, total=100, redisStock=99, mysqlAvailable=100, sold=0, redisDiff=1, mysqlDiff=0, result=疑似少卖`（21:17:31.810）

## 9. QPS 回退分析

> 本节基于 `logs/flash-sale-system.log`、压测当时 JTL 归档值与 Windows 事件日志的既有数据定位回退原因，**未重跑压测、未改代码**。所有数字均为实测取证值。

### 9.1 现象

- **buy QPS 中位（r1~r4）303.1**，v3 为 469.5（**-35%**），低于 §2 护栏目标 ≥ 422。
- **buy P99 中位（r1~r4）660.6 ms**，v3 为 397 ms，高于 §2 护栏目标 ≤ 476 ms。
- 轮间波动大：buy QPS 逐轮 `r0=396.0 / r1=258.4 / r2=366.3 / r3=347.8 / r4=209.4`（区间 **209~396**）；buy P99 逐轮 `r0=469 / r1=756 / r2=538 / r3=565 / r4=939`。
- r4 尾部集中 **42 条** `SlowSqlInterceptor` WARN，时间戳 `20:38:03.315 → 20:38:03.677`（362 ms 内爆发，恰在 r4 结束点之前）。

### 9.2 排除项

**① Job 干扰 —— 排除。** 三个 Job 在 v4 压测窗口（20:34:57–20:38:03）内全程在跑，但全部空转、毫秒级：

| Job | 周期 | 窗口内次数 | 单次耗时 | 命中 |
|---|---|---:|---|---|
| JOB-01 `findExpiredUnpaid` | 30 s | 7 | 1–5 ms | `Total: 0` |
| JOB-02 `reclaimStale`+`findDue` | 15 s | 13 | 4–13 ms | `Updates: 0` / `Total: 0` |
| JOB-03 对账 | 5 min | 0 | — | 唯一临近窗口的 20:37:31.610 落在 r3→r4 轮间空档，不与任何 burst 重叠 |

窗口内 3 分钟 Job 累计 DB 耗时约 **100 ms**（JOB-01 约 20 ms + JOB-02 约 81 ms），无任何一次 Job 足以解释 -35% → 排除。

**② accept-count 变更（100→200）—— 非回退来源。** 该变更只消除建连拒绝；v4 全轮 `Connection refused` = 0（对比 v3 r1/r3 的 51/33），而 v3 中无拒绝的 r2/r4 仍达 469.5/435.7。消除拒绝不能解释吞吐系统性下降 → 排除。

**③ 业务逻辑 —— 无退化。** 数据正确性全过：diff=0、超卖=0、重复订单=0、5xx=0（见 §3）。回退仅体现在延迟/吞吐维度，非正确性问题。

### 9.3 主因：环境抖动（宿主磁盘 I/O 争用）

Windows 事件日志显示 v4 压测窗口 **20:34:57–20:38:03（2026-10-21）** 内宿主密集发生：

| 时间 | 事件 | 含义 |
|---|---|---|
| 20:35:48 | VSS 8231 | 卷影副本服务启动 |
| 20:35:51 | Kernel-General 16 | 清理注册表配置单元 |
| 20:35:55 | WindowsUpdateClient 44 | **Windows 更新开始下载更新** |
| 20:36:13–15 | ESENT 102/300/301/302/105/326 | **`DS_Token_DB` 引擎启动 + 重放日志 + 恢复** |
| 20:37:10 / 20:39:14 | SCM 7040 | BITS 服务启动类型切换（下载关联） |
| 20:37:45 | Volsnap 33 | 删除 C: 旧卷影副本 |
| 20:38:51 | VSS 8224 | 卷影副本删除 |

**卷影副本写入/删除 + Windows Update 下载 + ESENT 数据库恢复三者与压测窗完全重叠**，造成宿主磁盘 I/O 争用；Docker 中的 MySQL/Redis 共享该磁盘，读写被拖慢。应用侧无异常（全程仅 1 条 ERROR 在窗口外 20:13:36、42 条 WARN 全是慢 SQL、无 Hikari 超时、无重启、无 GC/OOM、窗口内无卡顿）。

**⚠️ 跨天不可比（诚实标注）：v3 数据取自 2026-10-20，v4 取自 2026-10-21，非同一批次、同一环境基线。** v4 全轮系统性约 2x 慢于 v3（不止尾部），符合"宿主持续 I/O 干扰"特征。**因此本节的 -35% 不能作为代码退化的结论，仅能判为环境差异。**

### 9.4 放大因子：Hikari 连接池排队

- `maximum-pool-size=10` 在 200 并发下成为瓶颈。`SlowSqlInterceptor` 计时口径为 `invocation.proceed()` 全程，**包含从 Hikari 取连接的等待**。
- r4 的 **42 条慢 SQL 全部为 `SeckillActivityMapper.selectById`**（热点活动行 id=2 主键读），耗时 `min=508 / p50=615 / p90=785 / max=790 ms`，**100% 落在 [500,1000) ms，无一条 ≥ 1000 ms**。
- 主键读本身亚毫秒；500–790 ms 绝大部分耗在**等连接**，是连接池在并发 + 慢 SQL（环境 I/O 拖慢）双重压力下的排队症状，而非查询变慢。

### 9.5 结论与判定

**v4 数据正确性全过；QPS/P99 回退判定为环境干扰（Windows Update + 卷影副本 + ESENT 与压测窗重叠致宿主磁盘 I/O 争用），叠加连接池=10 放大为排队，非代码/逻辑问题。** 因 v3/v4 跨天不可比，本轮不据此判定 v4 触发性能护栏失败（**挂起，待复测**）。

### 9.6 建议（决定性验证，均未执行）

1. **同环境对照复测**：同一天、关闭 Windows Update/卷影副本后台后重跑 v3 场景 —— 若 v3 也掉到 ~300，坐实环境；若 v3 仍 ~469，才回查代码/配置。
2. **生产级复测**：Linux 生产环境复测，脱离本机 Windows 后台干扰，得到可比基线。
3. 可选：Hikari `maximum-pool-size` 从 10 上调后复测，验证连接池是否为独立瓶颈（一次只动一个变量以保证可归因）。

## 11. 结论

- **一致性闭环（v4 核心目标）**：**全部达成**——
  - 超时取消：过期 `UNPAID` 在 ≤ 2 扫描周期内进入 `CLOSED_TIMEOUT`（实测 2s 关闭），`close_reason=1`/`close_time` 正确；
  - 库存回补：Redis/MySQL 各精确 +1、幂等标记 `seckill:refund:{orderNo}` 生效、补偿记录恰好 1 条 SUCCESS；
  - 三方对账：单侧差异 1 周期内检出（`redis_diff=1`/`result=2`），**只告警不改数**，恢复后归零，append-only 三行流转完整；
  - traceId 跨 MQ：Producer/Consumer traceId 完全一致，无断链。
- **正确性护栏**：全 5 轮超卖=0、重复=0、双 diff=0、5xx=0、业务码 `0:100/2008:100`（受理数=库存数=100）——**全部通过**。
- **accept-count**：5 轮 `Connection refused` 合计=0（v3 为 51/33），修复有效（附 §5 混杂因素诚实标注）。
- **性能护栏**：buy QPS 303.1 < 422、P99 660.6 > 476，**原始值触碰护栏**；经 §9 诊断为**环境干扰 + 跨天不可比**，非代码退化，**判定挂起、待 Linux/同环境复测**，不据此判 v4 失败。

**一句话结论**：v4 的功能目标（超时取消 + 库存回补 + 三方对账 + 可观测 + accept-count）与正确性护栏**全部实测通过**，QPS 表面回退定性为宿主环境干扰且待复测澄清 —— **v4 可交付**，性能护栏结论保留至同环境/Linux 复测后再判。
