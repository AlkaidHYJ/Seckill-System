## 2. 关键决策

### ADR-019：超时关闭 + 库存补偿

- **JOB-01（`TimeoutCloseJob`，`fixedDelay=30s`，批量 100）**：扫描 `status='UNPAID' AND pay_deadline < NOW()`（命中 `idx_status_deadline`），逐单 CAS `UNPAID → CLOSED_TIMEOUT`（`close_reason=1`、写 `close_time`）；CAS 影响行数=1 才迁移，与支付 `payIfUnpaid` 的双向 CAS 保证关闭/支付只有一个成功。
- **同事务建补偿单**：CAS 与 `TIMEOUT_REFUND(PENDING)` 插入在同一事务原子提交，消除「已关闭但无任务」的孤儿窗口；唯一键 `uk_compensation_order_type` 兜住并发重复建单。
- **JOB-02（`StockCompensationJob`，`fixedDelay=15s`，批量 50）**：先 CAS 领取 `PENDING → COMPENSATING`，再执行 Redis 回补 Lua（`INCR` 库存 + `DEL` 限购标记 + 写 `seckill:refund:{orderNo}` 标记）→ MySQL `available_stock+1`（条件 `available_stock < total_stock` 防超还）与 `COMPENSATING → SUCCESS` 同事务。
- **失败退避**：`retry_count+1`，10s/30s/2min 指数退避回 `PENDING`，累计 3 次置 `FAILED` 并告警，只告警不自动修复。崩溃恢复由 `reclaimStale`（卡死 > 5min 的 `COMPENSATING` 退回 `PENDING`）兜底。

### ADR-020：三方对账

- **JOB-03（`ReconciliationJob`，`fixedDelay=5min`，仅扫 `ONGOING`）**：对每个进行中活动计算 `redis_diff = total - redis_stock - sold`、`mysql_diff = total - available_stock - sold`（`sold = SUM(quantity) WHERE status IN (UNPAID,PAID)`）。
- **在途豁免**：存在 `PENDING`/`COMPENSATING` 补偿任务时，差异归因在途、走**豁免告警**不报不一致；`FAILED` **不豁免**（视为需要人工介入的真实差异）。
- **落库**：`reconciliation_record` append-only 快照，`result` 为 DDL `tinyint`（0 一致 / 1 疑似超卖 / 2 疑似少卖），batch traceId = `job03-{yyyyMMddHHmmss}`。
- **只告警不改数**：检出差异仅记录 + `log.error`，不修改 `orders`/`available_stock`/Redis；计数器 `seckill.reconciliation.inconsistent/exempted/redis_missing/failed`。

### ADR-021：可观测

- **traceId 跨 MQ**：`TraceIdFilter` 取 `X-Request-Id`（缺省生成）写 MDC → Producer `MessagePostProcessor` 把 MDC traceId 写入 AMQP header `traceId` → Consumer 取 header 回填 MDC；logback pattern 每行渲染 `[traceId=%X{traceId:-N/A}]`。**不改消息体**。
- **慢 SQL**：`SlowSqlInterceptor` 仅对 `SELECT/UPDATE` 生效，阈值默认 500 ms（可 `SECKILL_SLOW_SQL_THRESHOLD_MS` 覆盖），超阈值打 WARN。
- **指标清单**（Micrometer，仅 `/actuator/metrics` + 结构化日志，不引 APM）：`seckill.request.total{code}`、`mq.send.success/fail`、`mq.consume.success/fail/retry`、`seckill.timeout.closed/failed`、`seckill.compensation.refunded/skipped/retried/alerts`、`seckill.creating.compensation.processed/skipped/failed/alerts`、`seckill.reconciliation.inconsistent/exempted/redis_missing/failed`、`seckill.reconciliation.diff.total{type}`。

## 5. 已知限制汇总

### 承接 v3（延续未解）

- IP 维度限流仅有代码证据，缺独立实测样本（同机单 IP 无法触发）。
- `token → buy → UNPAID` 端到端收敛时延未量化 P50/P95/P99。
- 缺 CPU、GC、MySQL 锁等待、RabbitMQ 消费延迟等资源级指标。
- DLX 失败消息仍需运维手工介入，无查看/重放/结果记录工具。
- 同机压测仅用于版本间相对比较，QPS 不能外推生产容量。

### v4 新增（ADR-021 §5 + 设计 §17.10 L1~L8）

- **只告警不自动修复**：补偿重试耗尽 `FAILED`、对账检出差异均不改数，依赖人工介入（设计 17.8-9）。
- **补偿 `FAILED` 残窗**：存在「Redis 已回补、MySQL 未归还」的中间态，仅由下一轮对账 `mysql_diff` 检出。
- **补偿参数未外提**：JOB-01/02 间隔、批量、退避序列、`reclaimStale` 判死阈值以常量实现（ADR-019 §5），调参需改代码。
- **无 `user_id` 列**：订单表缺用户维度索引，按用户排查需回表或走 Redis 标记。
- **计时依赖应用时钟**：`pay_deadline`、退避、JOB 周期均以应用时间判断，未做多实例时钟一致性兜底。
- **调度单实例假设**：JOB 幂等可容忍重复触发，但未验证多实例并发调度下的争抢与重复扫描成本。
- **traceId 仅覆盖入口与 MQ**：异步线程池内新建任务的 traceId 不自动延续（沿用 MDC 边界）。
- **指标 params 暂不脱敏**（ADR-021）；`mq.consume.retry` 口径为「实际重试次数」；`seckill.request.total` 仅埋 `buy` 端点，token 不埋。
- **`ENDED` 活动不参与对账**：活动结束后不再扫描，收尾差异需人工确认（设计 L6）。
- **对账仅在途豁免 `PENDING`/`COMPENSATING`**：`FAILED` 不豁免，可能与「待人工处理」窗口叠加产生噪声告警。

### v4 实测后新增（性能/环境/工程，诚实登记，不藏）

- **accept-count 在 Windows 下行为特殊**：v4 5 轮 `Connection refused` 全 0 是正向信号，但 v4 整体吞吐低于 v3（受下述环境干扰），**无法排除「压力降低」这一混杂因素**——严格说这是「未见复发」，不是同等压力下的证明；OS listen backlog 实现与端口耗尽亦受本机影响。
- **QPS 回退是环境干扰，非代码问题**：v4 buy QPS 中位 303.1 vs v3 469.5（-35%）、P99 660.6 vs 397，经取证定性为 **Windows Update + VSS 卷影副本 + ESENT 恢复与压测窗重叠致宿主磁盘 I/O 争用**；且 **v3=2026-10-20、v4=2026-10-21 跨天采集，非同一环境基线，不可直接对比**。正确性护栏全过。护栏性能判定挂起待复测。
- **Hikari `pool=10` 在 200 并发下是瓶颈**：`maximum-pool-size=10` 使 200 并发取连接排队；慢 SQL 观测口径含取连接等待，42 条 WARN 全为热点行 `selectById` 主键读（508–790 ms）。本轮按「一次只动一个变量」未调参，列入 backlog。
- **商品维度限流未做**：ADR-018 本批仅用户/IP 两维，商品（活动）维度限流未启用；热点活动保护依赖 token/path + 库存 Lua。
- **IP 限流 NAT 误伤需生产标定**：依赖 `remoteAddr`，共享出口下 200 用户同 IP，同机压测无法触发、阈值需生产环境按真实网络拓扑标定；可信来源需在网关层治理。
- **无 `src/test` 自动化测试**：本仓库当前**无端到端/集成自动化测试**，v4 一致性闭环依赖手工功能轮（场景 2/4/6）+ 压测对账验证；回归保障薄弱，是主要工程质量债。
- **逐轮 P95 未随轮归档**：仅保留 r1~r4 中位 624.6 ms；JTL 原始件未纳入版本库，逐轮明细不可复现。

## 6. backlog

> 下一步候选，按「面试时能讲清动机、边界与代价」排序。

### 首要（性能定论与质量兜底，v4 收尾后第一批）

- **Linux/同环境复测验证真实 QPS**：关闭 Windows Update/卷影副本后台或迁到 Linux，重跑 v3 对照轮 + v4 轮，得到可比基线，坐实/推翻「环境干扰」定性。
- **Hikari `pool` 调到 20 复测**：一次只动 `maximum-pool-size`（10→20），验证连接池是否为独立瓶颈（慢 SQL/取连接等待是否显著下降）。
- **补 `src/test` 集成测试**：为超时取消→回补幂等、对账双 diff 判定、token/path 防重放、限流补端到端/切片测试，替代手工功能轮，收紧回归保障。
- **接 Prometheus + Grafana**：把 §17.6 指标清单从 `/actuator/metrics` 拉取升级为常驻采集 + 告警规则（含「JOB 侵扰 buy P99 ≤ 10%」看板）。
- **商品维度限流**：在用户/IP 之外补活动（商品）维度滑动窗口限流，保护热点活动，配合生产 IP 阈值标定。

### 一致性兜底（承接 v4 残窗）

- 对账检出差异后的**半自动修复**：白名单场景（如确定无在途补偿的 `redis_diff` 单向偏差）提供受控修复入口，保留审计，避免全自动改数。
- 补偿链路**自愈增强**：`FAILED` 任务的可观测看板 + 一键重放（复用 MQ 重放工具），替代纯人工。
- Publisher Confirm 不确定窗口的差异检测与恢复流程（v3 backlog 延续）。

### 可观测与容量

- 接入 Prometheus + Grafana，落地 §17.6 指标清单的告警规则（而非仅 `/actuator/metrics` 拉取）。
- 补齐资源级指标（CPU/GC/连接池/锁等待/MQ 消费延迟），把「JOB 侵扰 buy P99 ≤ 10%」做成常驻看板。
- traceId 向异步线程池、`@Async`、定时任务内部传播延伸（MDC 边界扩展）。

### 接入与防刷

- IP 维度限流的独立实测（多源 IP 或独立 key 构造）。
- `accept-count` 若在本机仍 refused，转向**网关层/更真实环境**验证 backlog 上限（区分应用与 OS listen backlog）。
- 端到端收敛时延（`token → buy → UNPAID → 收敛`）P50/P95/P99 的量化埋点。

### 工程化

- JOB-01/02/03 调度参数与判死阈值**配置化外提**（ADR-019 §5 预留）。
- DLQ 消息查看、人工重放与处理结果记录（v3 backlog 延续）。
- 多实例调度验证：确认幂等 CAS + 唯一键在并发调度下的争抢成本与正确性。

## 7. 已知代价

- **对账只增不改**：`reconciliation_record` append-only，长期增长需要归档策略。
- **补偿为最终一致**：回补非实时，依赖 JOB 周期（15s/30s），期间库存短暂偏低（fail-close，不超还）。
- **三方对账周期 5min**：差异发现存在最长一个周期的延迟，靠 `FAILED` 告警补充即时性。
- **串行回补吞吐有限**：JOB-02 批量 50 + 逐单执行，突发大量超时会堆压补偿队列，靠退避消化。
